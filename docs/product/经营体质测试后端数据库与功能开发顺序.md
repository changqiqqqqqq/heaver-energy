# 经营体质测试后端数据库与功能开发顺序

版本：v0.1
适用范围：`services/api` FastAPI 后端、MySQL/Alembic 迁移、经营体质测试到线索运营闭环
来源：基于「经营体质测试需求开发设计文档」和当前后端实现差距整理

---

## 1. 调整目标

当前后端已经具备认证、用户、问卷题库和答题记录的基础结构，但还没有形成完整的获客运营闭环。调整后的后端目标是：

```text
小程序用户
  -> 完成经营体质测试
  -> 后端计算 CP/MA/SR/EP/AM/LV 六维得分
  -> 生成星级、唯一画像、A/B/C/D 线索等级
  -> 自动创建或更新线索
  -> 结果页继续承接初筛、服务需求、账单上传
  -> 后台运营查看线索、跟进、备注、转供应商
  -> 敏感操作写入审计日志
```

本文件按修复顺序整理调整后的数据库字典、表结构和后端功能开发顺序。

---

## 2. 当前实现需要调整的点

| 范围 | 当前状态 | 调整后要求 |
|---|---|---|
| 数据底座 | 实际迁移只包含用户、后台管理员、问卷核心表 | 补齐企业、线索、CRM、初筛、需求、文件、账单、供应商、审计、权限表 |
| 问卷维度 | `score_json` 支持任意 key，测试仍使用 `cost` | 统一使用 `CP`、`MA`、`SR`、`EP`、`AM`、`LV` |
| 画像 | 当前按 `rule_json` 或 `profile_bias` 简单匹配 | 固定优先级输出唯一画像：隐性浪费、能源觉醒、供应商困惑、成本敏感、增长扩张、稳健经营 |
| 线索 | `lead` 模块为空，答题只保存 `lead_id` 数字 | 答题提交后自动创建或更新 `leads` |
| 线索等级 | 旧文档为 A/B/C | 新口径为 A/B/C/D |
| 结果页 | 结果快照只有基础 profile 信息 | 保存画像文案、行业参照、信号、CTA、免责声明、星级 |
| 后台运营 | 路由已注册但模块为空 | 支持线索列表、详情、跟进、备注、转供应商、状态流转 |
| 安全审计 | 权限和审计模块为空 | 查看敏感信息、下载账单、转供应商、状态修改必须写审计 |

## 3. 数据库设计原则

1. 表名、字段名统一使用小写 `snake_case`。
2. 主键使用 `BIGINT UNSIGNED AUTO_INCREMENT`，SQLite 测试环境可用 `Integer` 变体。
3. 状态字段使用 `VARCHAR(32)`，不使用 MySQL `ENUM`。
4. 金额、电量字段使用 `DECIMAL`，时间使用 `DATETIME(3)`。
5. 业务快照、配置、标签使用 `JSON`。
6. 线索与答题结果必须保存快照，避免后续问卷版本、画像文案变化影响历史记录。
7. 手机号只保存脱敏值、密文、哈希值，不保存明文。
8. 敏感文件默认私有访问，后台查看和下载必须写审计日志。

## 7. 后端功能开发顺序

### 阶段 0：口径与基础枚举

目标：先把业务常量定死，避免后续模块各写一套。

开发内容：

1. 在 `app/common/enums.py` 或独立常量模块中定义：
   - 六维评分：`CP`、`MA`、`SR`、`EP`、`AM`、`LV`
   - 线索等级：`A`、`B`、`C`、`D`
   - 画像编码：`cost_sensitive`、`hidden_waste`、`growth_expansion`、`stable_operation`、`energy_awakened`、`supplier_confused`
   - 线索状态：`pending_followup`、`following`、`transferred_supplier`、`content_saved`、`closed`
   - 需求类型：用能、供应商推荐、报价复核、合同把关等
2. 调整现有测试，禁止继续使用 `cost` 这类旧维度示例。
3. 补充评分星级换算函数。

验收：

1. 单元测试能覆盖星级边界。
2. 所有新问卷种子数据只使用六维评分 key。

### 阶段 1：数据底座模块

目标：先让线索能被创建、查询和关联。

开发模块：

1. `enterprise`
   - `model.py`：实现 `Enterprise`、`EnterpriseContact`
   - `repository.py`：按用户、手机号 hash、企业 ID 查询和创建
   - `service.py`：创建或更新企业、联系人
2. `lead`
   - `model.py`：实现 `Lead`、`LeadStatusLog`
   - `repository.py`：创建线索、按用户查最近线索、按 ID 查详情、更新状态和快照
   - `service.py`：提供 `create_or_update_lead_from_questionnaire`
   - `router_admin.py`：先提供列表和详情接口骨架
3. Alembic 迁移 1
4. 更新 `app/db/base.py`，导入新增模型

关键业务规则：

1. 用户答题时没有企业信息，允许创建 `enterprise_id = NULL` 的线索。
2. 同一用户再次提交问卷，默认创建新的 submission，但可更新最近一条未关闭 lead。
3. 后续初筛、服务需求、账单上传需要合并到同一 lead。

验收：

1. 数据库能创建 `leads`。
2. 后台可查到基础线索列表。
3. 问卷提交可以关联或创建 lead。

### 阶段 2：问卷评分闭环

目标：让经营体质测试提交后返回可展示、可运营的结果。

开发模块：`questionnaire`

开发内容：

1. 扩展 schema：
   - 提交响应增加 `lead_id`、`lead_grade`、`dimension_stars`、`answer_tags`。
   - `result` 增加 headline、benchmark、signals、cta、disclaimer。
2. 扩展 service：
   - 校验 score key 只能是 CP/MA/SR/EP/AM/LV。
   - 累加六维得分。
   - Q1 区域题只写标签，不计分。
   - 得分转换为星级。
   - 按固定优先级匹配唯一画像。
   - 按 AM/LV 计算 A/B/C/D 等级。
   - 生成结果页完整快照。
   - 调用 `lead.service` 创建或更新线索。
3. 扩展 repository：
   - 保存增强后的 submission 和 answers 快照。
4. 种子数据：
   - 提供经营体质测试 v1 的题目、选项、评分、标签、画像、结果页配置。

画像优先级：

```text
1. hidden_waste
2. energy_awakened
3. supplier_confused
4. cost_sensitive
5. growth_expansion
6. stable_operation
```

线索等级规则：

| 等级 | 条件 |
|---|---|
| A | AM >= 8 且 LV >= 4 |
| B | AM 5-7 或 LV >= 3 |
| C | AM 2-4 |
| D | AM 0-1 |

验收：

1. 提交答题后返回 `lead_id`、六维分、星级、画像、线索等级。
2. `questionnaire_submissions` 保存完整结果快照。
3. `leads` 同步更新 `profile_code`、`lead_grade`、`score_snapshot_json`、`need_tags_json`。
4. 单测覆盖画像优先级冲突和 A/B/C/D 边界。

### 阶段 3：结果页承接能力

目标：结果页 CTA 能继续沉淀资料，并提升线索质量。

开发模块：

1. `screening`
   - 小程序提交免费初筛。
   - 创建或更新企业、联系人。
   - 更新 lead 的手机号授权、企业信息、最近活动。
2. `service_request`
   - 小程序提交服务需求。
   - 支持多需求类型。
   - 更新 lead 的 `primary_need_type` 和 `need_tags_json`。
3. `file` 和 `bill`
   - 上传账单文件。
   - 创建 `files` 和 `bill_uploads`。
   - 更新 `leads.has_bill_uploaded = 1`。
4. Alembic 迁移 3

小程序 API：

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | `/api/app/screening-requests` | 提交免费初筛 |
| POST | `/api/app/service-requests` | 提交服务需求 |
| POST | `/api/app/files` | 上传文件 |
| POST | `/api/app/bills` | 关联账单上传记录 |

验收：

1. 结果页提交初筛后，后台线索详情能看到初筛信息。
2. 上传账单后，线索列表 `has_bill_uploaded` 变为 true。
3. 服务需求能驱动后台按需求类型筛选。

### 阶段 4：后台线索运营能力

目标：运营人员能在后台完成线索处理。

开发模块：

1. `lead`
   - 列表筛选：等级、画像、状态、需求、是否上传账单、是否授权手机号、时间范围。
   - 详情聚合：企业、联系人、答题结果、初筛、服务需求、账单、跟进、备注、转供应商。
   - 状态流转：待跟进、跟进中、已转供应商、内容留存、关闭。
2. `crm`
   - 新增跟进记录。
   - 新增备注。
   - 更新 `leads.last_activity_at`。
   - 必要时更新 `lead_status`。
3. `supplier`
   - 供应商列表。
   - 转供应商。
   - 写入 `supplier_transfers`。
   - 更新 `leads.lead_status = transferred_supplier`。
4. Alembic 迁移 4 中的 CRM 和供应商部分。

后台 API：

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/admin/leads` | 线索列表 |
| GET | `/api/admin/leads/{lead_id}` | 线索详情 |
| POST | `/api/admin/leads/{lead_id}/status` | 更新线索状态 |
| POST | `/api/admin/crm/followups` | 新增跟进 |
| POST | `/api/admin/crm/notes` | 新增备注 |
| GET | `/api/admin/suppliers` | 供应商列表 |
| POST | `/api/admin/suppliers/transfers` | 转供应商 |

验收：

1. 后台能按 A/B/C/D 和画像筛选线索。
2. 线索详情能完整展示答题快照和运营建议。
3. 跟进、备注、转供应商都能写入时间线。

### 阶段 5：权限与安全审计

目标：敏感数据访问可控、可追踪。

开发模块：

1. `security_audit`
   - 写入审计日志。
   - 查询审计日志。
2. `auth` / `permissions`
   - 角色权限表。
   - 管理员权限加载。
   - router 层权限依赖。
3. 敏感接口：
   - 查看完整手机号。
   - 查看或下载账单。
   - 转供应商。
   - 修改线索状态。

后台 API：

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/admin/leads/{lead_id}/sensitive` | 查看敏感联系方式 |
| GET | `/api/admin/files/{file_id}/signed-url` | 获取私有文件临时访问地址 |
| GET | `/api/admin/audit-logs` | 查看审计日志 |

验收：

1. 无权限不能查看完整手机号或下载账单。
2. 每次敏感查看都写入 `audit_logs`。
3. 审计日志能按操作人、对象、动作筛选。

### 阶段 6：统计、分享与渠道

目标：后台可以看到运营概览，分享回流可统计。

开发模块：

1. `statistics`
   - 总线索、今日新增、A/B/C/D 数量、待跟进、已转供应商。
   - 按画像、需求类型统计。
   - 留资转化率、账单上传率。
2. `share`
   - 如果继续沿用 `file` 模块生成分享卡，至少记录 `share_cards` 和 `share_events`。
   - 访问、扫码、提交事件可回写 lead。

后台 API：

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/admin/dashboard/summary` | 统计概览 |
| GET | `/api/admin/dashboard/profiles` | 画像分布 |
| GET | `/api/admin/dashboard/conversions` | 转化指标 |

验收：

1. 后台首页有基础统计。
2. A 类线索数量、待跟进数量准确。
3. 分享回流事件可以关联到用户或线索。
